# Анализ требований и проектные решения
## Ключевые требования бизнеса

|Требование|Значение|
|----|----|
|Пиковая нагрузка|	2500 одновременных пользователей|
|Максимальное время ожидания|	60 секунд от страховых компаний|
|Отображение результатов|	По мере поступления (стриминг)|
|Количество страховых компаний|	10+ (с учётом планов по расширению)|

## Проектирование osago-aggregator
### Требуется ли своё хранилище данных?
    ДА, требуется. Обоснование:
|Причина|Комментарий|
|----|----|
|Длительные операции|Опрос страховых компаний может занимать до 60 секунд|
|Отказоустойчивость|	При падении сервиса состояние запросов должно сохраняться|
|Масштабирование|	Несколько экземпляров должны видеть общее состояние|
|Повторные запросы|	При ошибках нужна информация о статусе заявки|

Предлагаемое решение: PostgreSQL как основное хранилище

### API для core-app
    - POST /api/v1/osago/requests -   Создание новой заявки на ОСАГО
    - GET /api/v1/osago/requests/{request_id}/offers -   Получение всех оступных предложений
    - GET /api/v1/osago/requests/{request_id}/stream -  Server-Sent Events (SSE) - стриминг результатов по мере поступления

### Интеграция между core-app и osago-aggregator
    Выбрано: REST + Server-Sent Events (SSE)
    Почему не Kafka:
        - Требуется низкая задержка (стриминг в реальном времени)
        - Результаты нужны конкретному пользователю, а не всем сервисам
        - Проще реализовать SSE для HTTP-клиентов

|Компонент|	Протокол|	Назначение|
|----|----|----|
|core-app → osago-aggregator|	REST (HTTP/2)	Создание заявки, получение офферов|
|osago-aggregator → core-app|	SSE	Стриминг результатов (Web-клиент получает через WebSocket)|
|core-app → WebSocket|	WebSocket	Передача стрима клиенту|

## API для веб-приложения
### REST API (core-app)
    - POST /api/v1/osago/application - Создание заявки
    - GET /api/v1/osago/offers/{application_id} - Получение всех предложений (если клиент отключился и переподключился)

### WebSocket для стриминга
### Интеграция веб-приложения с core-app
|Назначение|	Протокол|	Обоснование|
|----|----|----|
|Отправка формы	REST/HTTPS|	Просто, надёжно, стандартно|
|Получение результатов	WebSocket|	Низкая задержка, двусторонняя связь|
|Переподключение	REST + WebSocket|	Клиент может восстановить сессию|

## Паттерны отказоустойчивости
### Конфигурация паттернов
|Паттерн|	Где применяется|	Конфигурация|	Обоснование|
|----|----|----|----|
|Rate Limiting|	core-app → API Gateway|	100 RPS на пользователя|	Защита от DDoS и "шумных соседей"|
|Circuit Breaker|	osago-aggregator → каждая страховая	Failure |threshold: 50% Window: 60s Open: 30s|	Изоляция проблемных компаний|
|Retry|	osago-aggregator → страховые|	Max attempts: 3 Backoff: 100ms, 200ms, 400ms|	Временные сетевые проблемы|
|Timeout|	osago-aggregator → страховые|	Connect: 2s Read: 5s|	Не ждать долго|
|Timeout|	core-app → osago-aggregator|	65s (чуть больше 60s)	|Учитывать время на обработку|
|Bulkhead|	osago-aggregator|	Max concurrent requests: 500|	Не перегружать сервис|

## Итоговое решение
|Задача|	Решение|	Обоснование|
|----|----|----|
|Хранилище osago-aggregator|	PostgreSQL|	Длительные операции, отказоустойчивость|
|API для core-app|	REST + SSE|	Стриминг результатов, простота|
|Интеграция core-app ↔ osago-aggregator|	HTTP/2|	Высокая производительность|
|API веб-приложения|	REST + WebSocket|	Низкая задержка, стриминг|
|Интеграция веб-приложение ↔ core-app|	WebSocket + REST	|Сочетание надёжности и скорости|
|Rate Limiting|	API Gateway|	Защита от перегрузок|
|Circuit Breaker|	osago-aggregator → страховые|	Изоляция сбоев|
|Retry	|osago-aggregator → страховые|	Временные ошибки|
|Timeout|	Все внешние вызовы	|Предсказуемость|
|Bulkhead	|osago-aggregator|	Не перегружать сервис|
|Session Affinity	|WebSocket соединения	|Сохранение состояния|
