# Анализ существующего REST API сервиса client-info
## Текущая структура REST эндпоинтов
    Проблемы текущего подхода:
    - Избыточное количество запросов — для получения полной информации о клиенте нужно сделать 3 отдельных запроса
    - Высокий RPS — каждый сценарий генерирует множество вызовов
    - Over-fetching / Under-fetching — либо слишком много данных, либо слишком мало
    - Сложность поддержки — 500+ атрибутов распределены по разным ресурсам

|Эндпоинт|	Метод|	Возвращаемые данные|	Назначение|
|----|-----|-----|-----|
|/clients/{id}|	GET|	Client (id, name, age)|	Базовая информация о клиенте. Получить информацию о клиенте по ID|
|/clients/{id}/documents|	GET|	[Document]	|Список документов клиента. Возвращает список документов клиента по ID.|
|/clients/{id}/relatives|	GET|	[Relative]|	Информация о родственниках. Возвращает информацию о родственниках клиента по ID.|

## Сравнение REST vs GraphQL
|Аспект|	REST|	GraphQL|	Преимущество GraphQL|
|----|----|----|-----|
|Количество запросов для полного профиля|	3|	1|	Снижение RPS в 3 раза|
|Объём передаваемых данных|	Фиксированный|	Только запрошенные поля|	Нет over-fetching|
|Гибкость|	Низкая (нужны новые эндпоинты)|	Высокая (клиент выбирает поля)|	Быстрая адаптация|
|Версионирование|	Новые версии API|	Эволюция схемы|Обратная совместимость|
|Документирование|	Swagger/OpenAPI|	Self-documenting (Introspection)| Автоматическая документация|
|Типизация|	Слабая (JSON)|	Строгая (GraphQL Schema)| Валидация на уровне схемы|
