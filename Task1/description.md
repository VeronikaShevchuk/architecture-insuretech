# Стратегия масштабирования и отказоустойчивости

## Анализ текущей ситуации
    Текущая архитектура:  единая VM с PostgreSQL, один кластер Kubernetes в одной зоне доступности
    Проблемы: падения при недоступности, медленная загрузка, нарушение SLA для B2B
    Требования: 99.9% доступности, RTO 45 мин, RPO 15 мин, рост в регионах РФ

## Выбор стратегии масштабирования
|Компонент|	Стратегия|	Обоснование|
|---|---|---|
|Stateless сервисы (core-app, client-info, aggregators)|Горизонтальное масштабирование (HPA)|Эффективнее вертикального: позволяет распределять нагрузку, дешевле, даёт отказоустойчивость|
|Stateful компоненты (БД)|Вертикальное масштабирование + репликация|PostgreSQL плохо масштабируется горизонтально (шардирование избыточно для 50 ГБ)|
|Кэш (Redis)|Горизонтальное масштабирование (кластер Sentinel)|Обеспечивает отказоустойчивость и распределение нагрузки чтения|

## Зоны доступности
    Решение: Использование 3 зон доступности (ru-central1-a/b/c)
    Трёхзонная конфигурация критически необходима для достижения 99.9% SLA:
        - Одна зона — максимум 99.5% доступности
        - Три зоны — возможность потери целой зоны без остановки сервиса


## Конфигурация развёртывания в Kubernetes
    Выбор: Один растянутый кластер (Regional cluster)
    Преимущества единого кластера:
        - Единый control plane — проще управление и мониторинг
        - Отсутствие сложностей с cross-cluster networking
        - Встроенная поддержка федерации ресурсов
        - Yandex Managed Kubernetes гарантирует HA control plane (распределён по зонам)
        - Проще обновления и rollout новых версий
    Независимые кластеры потребовали бы:
        - Дополнительных инструментов для service mesh
        - Сложной балансировки между кластерами
        - Удвоения operational overhead
    Конфигурация (Региональный Managed Kubernetes кластер):
        - Control plane (распределён по 3 зонам)
        -  Node group А (ru-central1-a): HPA min=2, max=10, CPU 70%
        - Node group B (ru-central1-b): HPA min=2, max=10, CPU 70%
        - Node group C (ru-central1-c): HPA min=2, max=10, CPU 70%

## Балансировка нагрузки
    Многоуровневая архитектура балансировки
        - Пользователь/B2B
        - Global DNS (Latency-based routing) - направляет в ближайший регион
        - Yandex Network Load Balancer (NLB) - глобальный, проверка здоровья зон
        - Yandex L7 Application Load Balancer (Regional) - балансировщик между зонами A, B, C
        - Kubernetes Ingress / Services
        - API Gateway — rate limiting для B2B (20 RPS на партнёра)
        - Backend Services

## Health Checks
    Отражены на схеме:
        - L7 ALB → Pods: HTTP GET /healthz, timeout 5s, interval 10s, threshold 2
        - NLB → ALB listeners: проверка доступности listener в каждой зоне
        - Readiness probes в Kubernetes: определяют готовность пода принимать трафик
        - Liveness probes для автоматического перезапуска зависших подов


## Фейловер-стратегия
    Active-Active
        Принцип работы:
            - Все три зоны являются primary (активными)
            - Трафик распределяется между зонами через NLB + DNS (latency-based)
            - При отказе одной зоны:
                - Health checks NLB фиксируют недоступность listener'ов в зоне (3 неудачные проверки)
                - NLB исключает зону из балансировки (время конвергенции < 1 мин)
                - Трафик перенаправляется в оставшиеся здоровые зоны
                - Клиентские библиотеки реализуют exponential backoff при повторных попытках

## Конфигурация базы данных
    Архитектура HA-кластера
        Managed PostgreSQL HA Cluster
            - Master (зона A) — принимает запись
            - Sync Replica (зона B) — синхронная репликация (remote_apply)
            - Async Replica (зона C) — асинхронная репликация для чтения
            - Patroni orchestrator — автоматический фейловер

## Шардирование
    Решение: Шардирование НЕ требуется
    Обоснование:
        - Объём данных: всего 50 ГБ (легко помещается в один HA-кластер)
        - Прогнозируемый рост: даже при 10x росте (500 ГБ) вертикальное масштабирование эффективно
        - Шардирование добавит complexity без реальной пользы
        - Managed PostgreSQL поддерживает вертикальное масштабирование до 1 ТБ+ на инстанс
